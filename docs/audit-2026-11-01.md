# 项目审查报告 · onepay-shop-worker

- 审查日期：2026-11-01
- 范围：`src/`（Worker 后端）、`public/`（前台 3 页 + 后台）、`migrations/`、`tests/`、`README.md`、构建与部署配置
- 审查方式：通读全部代码 + `npm run check` + `npm test`（101 项全部通过）+ 端到端逻辑推演（本地 D1 迁移 + 一人付 mock）

---

## 0. 结论摘要

这是一个**工程质量明显高于平均水准**的项目：D1 事务、幂等编号、租约令牌、缓存代际失效、内容安全（转义 / 快照 / 归属校验）、"不确定即不交付"的支付原则都做对了，测试也覆盖了这些边界。

问题集中在三类：

1. **前台缺一个「商品详情」页面**——最重要的商品信息（`description` 详情、完整目录、交付说明）用户根本看不到，卡片点进去只是把标题丢进搜索框。这是本报告**最高优先级**的体验问题。
2. **几处前后端字段对不上、状态算错**——「已使用积分」永远是错的、首页积分徽章永远不显示、后台 `withBusy` 的"恢复原状态"是空操作。
3. **缺少基础防护/自助能力**——登录接口没有任何频率限制（可被离线爆破），用户不能自己改密码，后台订单列表没有分页与筛选。

下面按模块给出全部发现，标注 `P0`（应尽快修）、`P1`（明显影响体验/运维）、`P2`（打磨项）。

## 1. 前台 · 信息架构与核心流程

### P0-1 没有商品详情页，商品详情字段从不展示
- 证据：`public/shop.html:218` 的卡片只有封面、标题、副标题、标签、价格、按钮；`public/index.html:139` 的卡片链接是 `/shop?q=<标题>`；`src/index.js` 里 `publicProduct()` 返回了 `description`（最长 4000 字）但**前端没有任何地方渲染它**。
- 影响：
  - 后台辛苦填的详情、交付说明、使用须知，用户永远看不到，只能盲买。
  - 商品无法被单独分享/收藏（没有稳定 URL），"复制链接发给朋友"这件事做不了。
  - 首页卡片用标题当搜索词跳转，标题里带空格或特殊字符就搜不到自己。
- 修复：新增 `GET /api/products/:id` + 独立页面 `/product?id=…`（含详情、目录、交付说明、相关推荐、同款兑换流程），首页/商品页卡片改为链接到详情页。

### P0-2 「已使用积分」恒为错误值
- 证据：`public/account.html:272` 读 `data.used`，但 `/api/access`（`src/index.js:986` 起）从来没返回 `used` 字段。
- 影响：永远走 fallback 分支，显示 `—` 或 `赠送N + ?`，用户无法知道自己在店里总共花了多少积分。
- 修复：`/api/access` 增加 `spent_points` / `onepay_used` / `order_count` / `pending_orders`，前端按新字段渲染。

### P0-3 「已购记录」统计数字与实际不符
- 证据：`public/account.html:351` 用「当前已加载这一页（最多 50 笔）」里 DELIVERED 的条数当总数，副标题也自认「最近 50 笔中的已交付订单」。
- 修复：改为服务端返回的累计已交付订单数。

### P0-4 首页积分徽章永远不显示
- 证据：三个页面都有 `<span class="points-chip hidden" data-points-wrap>`，但 `setPoints()` 只在 `shop.html` / `account.html` 里被调用；`index.html` 既不请求 `/api/access` 也不调用 `setPoints()`。
- 影响：登录用户在首页看不到自己有多少积分，"要不要先充值"这个决策没有依据。
- 修复：`Store.initChrome()` 在已登录时统一刷新积分徽章。

### P1-5 移动端积分徽章被彻底隐藏
- 证据：`public/storefront.css:204`（≤760px）`.points-chip { display: none; }`。
- 影响：手机上完全看不到余额，只能进个人中心查。
- 修复：移动端显示紧凑徽章（只保留数字）。

### P1-6 商品页排序不进 URL，刷新即丢失
- 证据：`public/shop.html` `syncUrl()` 只写 `category/tag/q`，`state.sort` 永远是初始化值 `recommended`；`#sortSelect` 变更后不写 URL。
- 影响：分享"按积分从低到高"的列表给别人，对方打开是另一个顺序；后退/前进也不生效。
- 修复：`sort` 进 URL 并在初始化时读取。

### P1-7 商品卡片不可点击、缺少"详情"入口
- 证据：`public/shop.html:218` 起卡片结构没有任何 `<a>` 包裹封面或标题。
- 影响：用户直觉是点卡片看图/看详情，点了没反应（只有按钮可点），是可感知的"按钮失灵"。
- 修复：封面 + 标题可点，并新增「查看详情」链接。

### P1-8 首页卡片把「已售罄」塞进圆形箭头按钮位
- 证据：`public/index.html` 中 `<span class="round-arrow" aria-label="查看商品">${soldOut ? '已售罄' : '↗'}</span>`。
- 影响：一个圆形箭头容器里塞了三个字，视觉溢出；且 `aria-label` 仍是"查看商品"。
- 修复：独立售罄标签 + 正确的无障碍文案。

### P2-9 头部搜索图标点了只是跳 `/shop`
- 在 `/shop` 页点它等于刷新当前页，不聚焦搜索框。建议跳 `/shop?focus=search` 并自动聚焦（低优先，未改）。

### P2-10 「忘记密码 / 修改密码」缺失
- 证据：`public/account.html` 账户信息面板写着"如需修改账号密码，请联系管理员在后台重置"。
- 影响：改密码这件事要人工介入，运营成本落在管理员身上。
- 修复：新增 `POST /api/auth/password`（校验当前密码）+ 账户信息面板里的改密表单。

### P2-11 个人中心首屏一次打 5 个接口
- `showDashboard()` 同时打 `/api/access`、`/api/product`、`/api/orders`、`/api/subscriptions`，即使 `/account?tab=profile` 也一样。
- 修复：改为「切到哪个 tab 才加载哪个」，已加载过的做缓存。
- 附带：切 tab 时不会自动刷新，用户会看到旧数据；保留显式「刷新」按钮。

### P2-12 支付入口每次点击都生成新的幂等编号
- 证据：`public/account.html` `buyPoints()` 里 `idempotency_key: 'buy-' + crypto.randomUUID()`。
- 影响：用户连点两次"支付宝充值"就会产生两条购买入口（不会重复扣费，但平台上会出现两条记录，且可能同时打开两个付款页）。
- 修复：同一 SKU 在 15 分钟内复用同一个编号（sessionStorage）。

### P2-13 模板字符串拼 onclick 的参数是 XSS 面
- 证据：`public/account.html:308` `onclick="buyPoints('${esc(option.sku_id)}', this)"`。`esc()` 把 `'` 转成 `&#39;`，浏览器在解析属性时会**先解实体再解析 JS**，所以含引号的 `sku_id`（来自一人付 `/product`）可以逃出字符串。
- 修复：去掉内联 onclick，改 `data-sku` + 事件委托。后台同类写法（`editGoods('${p.id}')` 等）参数都是本站生成的 `prd_/usr_/cat_` + UUID，风险低，暂不改，但建议后续统一。

### P2-14 空状态/错误态文案不统一
- 有的地方是"暂时无法读取…"+ 错误原文（直接把 `error.message` 抛给用户），有的地方只有"—"。建议统一为「发生了什么 + 可以做什么」，`P2` 打磨项。

## 2. 前台 · 兑换与交付逻辑

### 逻辑正确、值得保留的部分（不是问题，记录以确认审查覆盖面）

- 一人付成功必须 `status=SUCCEEDED && confirmed=true` 才交付；提交后超时/HTTP 异常/`UNKNOWN`/`PROCESSING` 一律保持 PENDING，不猜测、不重扣。`src/index.js` `consumptionResult()` / `processOrder()`。
- 赠送积分优先、余额不足才核销支付宝积分，金额在 D1 事务中预留并可原子退还（`src/bonus.js`）。
- 库存、赠送积分、订单、流水在同一个 `DB.batch()` 里提交；`refundOrder` 用 `processing_token` 做租约，过期请求不能退款。
- 订单保存交付内容**快照**，商品后续修改不影响已购用户。
- 订阅开通与订单交付同批提交，同一订单号重试不会二次延长（`src/subscriptions.js`）。
- 前端有「原订单编号重试」机制：`sessionStorage` 存 pending key + quote，刷新页面后继续用原编号，避免"扣了分却没交付"。

### P1-15 兑换失败后的引导不够
- `submitPurchase()` 拿到 4xx 就 `removeItem(slot)` 并把错误 toast 出来；但 `ORDER_ALREADY_PENDING`（有未确认订单）这种情况，正确动作是"去我的已购同步"，而 toast 只是一句话，用户不会自己跳过去。
- 修复：错误码映射成动作，`ORDER_ALREADY_PENDING` / `CONSUME_UNKNOWN` 直接给一个「去同步」按钮或跳转。

### P2-16 `purchaseDraft` 关闭弹窗后不清空
- `setModal('#purchaseModal', false)` 不重置 `purchaseDraft`，理论上残留旧 draft；`submitPurchase` 只靠按钮 id 绑定，实际不会误提交，属隐患级。

### P2-17 积分不足时的引导是"跳走"
- `buyProduct()` 里 `setTimeout(… '/account?tab=recharge', 600)`：先 toast 再强制跳页，用户来不及看清；建议留在原地并提供按钮。

## 3. 后台（`/admin`）

### P0-18 `withBusy()` 的状态恢复是空操作
- 证据：`public/admin.html:405` `const wasDisabled = button.disabled;` 在 `if (button.disabled) return;` **之后**执行，恒为 `false`；`:411` 再赋回去。
- 影响：语义上"恢复原状"实际是"一律解禁"。对 `#pairGenerate`（R2 未绑定时应保持 disabled）这类按钮，只要被 `withBusy` 包过一次就会被错误解禁，用户点了才发现后端 503。
- 修复：显式记录并恢复，同时保留"已禁用直接返回"。

### P1-19 成交订单没有分页、没有筛选
- 证据：`src/index.js:1235` `SELECT ... FROM orders ... LIMIT ?`，固定最多 100 条，没有 offset、没有状态筛选、没有按订单号/邮箱/商品名搜索、没有总数。
- 影响：订单多了以后第一页之后完全看不到，无法只筛"待确认"去人工对账（而 README 明确要求长期待确认要人工核对）。
- 修复：`status` / `q` / `offset` + `total` + `has_more`，后台加筛选条与上一页/下一页。

### P1-20 后台商品行没有"预览"入口
- 运营改完商品想看用户视角，只能自己打开商店去搜。修复：行内加「预览 ↗」链到 `/product?id=`。

### P2-21 交付方式是文件时，后台没有"下载/验证文件存在"的能力
- `file_key` 只能手填或上传，历史文件丢失时只有用户下载才会 404。建议后续加「检查文件」按钮（未做）。

### P2-22 「查看原数据」的 Monaco 是按需加载，失败有 textarea 兜底
- 实现正确，记录为无问题项（但 `admin-editor` 构建产物需要 `npm run build:editor`，见 §6）。

### P2-23 大量内联 `onclick`
- 可维护性与 CSP 兼容性都差（未来想上 `script-src` 严格策略就动不了）。属于技术债，未在本次改动。

## 4. 后端 / 接口 / 数据

### P0-24 登录接口零频率限制
- 证据：只有 Agent 配对有 `recordPairAttempt()` 限流；`/api/auth/login`、`/api/admin/login`、`/api/auth/register` 直接查库比对密码。
- 影响：PBKDF2-SHA256 100k 迭代在 Worker 上单次约几十毫秒，但接口本身不限次——攻击者可以持续撞库（尤其管理员入口），既消耗 CPU 也消耗 D1 读配额；一旦弱口令泄露，`admin` 角色即可改商品、改密钥。
- 修复：新增 `auth_attempts` 表（迁移 `0010`），按「IP + 邮箱」滑动窗口限制失败次数（15 分钟 8 次失败 → 429 + `retry-after`），登录成功清零；表结构缺失时 fail-open 以保证可用性。

### P1-25 注册失败把数据库原始报错回显给用户
- 证据：`src/index.js` `return fail(500, \`注册失败：${e.message}\`)`。
- 影响：可能泄露表名/约束名，也暴露内部状态。
- 修复：返回统一文案，细节只写 `console.error`。

### P1-26 Webhook 事件编号强类型比较
- 证据：`src/index.js:847` `parsed.id === eventId`。`parsed.id` 若是数字，与 header 里的字符串永远不相等。
- 修复：`String(parsed.id) === eventId`。

### P1-27 `/api/access` 缺字段导致前端无从渲染
- 见 P0-2，一并修。

### P2-28 没有 405
- 已知路径用了错误方法时返回 404 `Not Found`，调试时容易误判。属打磨项。

### P2-29 迁移编号重复
- `migrations/0009_agent_pairing.sql` 与 `migrations/0009_netdisk_scans.sql` 同为 `0009`。Wrangler 按文件名字典序执行，当前恰好能跑通，但：
  - 人工核对"迁移都应用了吗"容易漏；
  - 新建迁移必须用 `0010`，别再撞号。
  - **不要改名**历史迁移（已部署环境的 `d1_migrations` 以文件名记录，改名会导致重复执行）。

### P2-30 若干索引缺失（数据量大了才会痛）
- `orders(status, created_at)` 有；`admin_audit(created_at)`、`webhook_events(received_at)`、`purchase_intents(user_id, sku_id, created_at)` 没有。后者与 P2-12 的"复用购买入口"查询相关，本次迁移顺带补一个 `purchase_intents` 的索引。

### P2-31 `/api/admin/*` 大列表都没有分页
- 用户列表有（`limit/offset`），商品 `LIMIT 200` 硬编码，核销/购买记录固定 50。属可接受范围。

### 迁移与上线顺序

1. 备份 D1，暂停兑换与管理操作。
2. `npx wrangler d1 migrations apply onepay-shop --remote`（本次新增 `0010_auth_throttle.sql`）。
3. `npm run deploy`（`predeploy` 会重建 Monaco 编辑器产物）。
4. 验证：`/product?id=…` 可打开、首页卡片可点、登录失败 9 次返回 429、后台订单可筛选分页、个人中心统计与累计消费一致。
5. 注意前台 CSS/JS 引用版本号已升级为 `20261101-1`（`admin.css` 为 `20261101-3`），若再改样式需继续递增；HTML 外壳浏览器缓存 30 秒，上线后短时间可能仍看到旧页面。
